# Phase 2 legacy transaction backfill — proposed contract (no production writes yet)

## Non-negotiable
Preserve all existing transaction external_id, id, amount, currency, event_date, title, description, category, source, status and user memo. No insert, archive, delete, merge, amount correction or reclassification during metadata-only backfill. Existing metadata keys are preserved. Existing 106 rows are a collector-reported inventory, not an independently verified fact. Re-read current DB before planning.

## 1. Read-only inventory and one-to-one mapping
Collector submits a redacted plan summary and keeps row-level manifest in a secure authenticated channel, not GitHub. For each existing external_id, compare original source row by actual date/time, signed amount, merchant, card alias and source statement scope; include exact evidence reference and matching reason. Use opaque account alias, not PAN/card digits. Classify exact_unique, ambiguous, unmatched, conflict. Never resolve ambiguity by arbitrary ordering or matching totals alone. Exact amount/date/currency discrepancies require separate correction review, not metadata backfill. Report full coverage by classification, with separate counts for statement single-payment, installment, approval, cancellation/unbilled and unknown. Do not assume approval rows correspond one-to-one to statement rows; statement period/amount basis differs. Preserve all rows until reviewed.

## 2. Identity and scope
- Approval numbers can be shared by an approval and cancellation. Use provider-issued row ID if present; otherwise use a stable derived line identity based on original approval number + actual event type + provider event identifier or actual event timestamp/disambiguator. A derived identity is not provider-issued: propose a separate source_record_id_type=derived_line (requires agreed implementation); preserve original approval number in metadata.approval_no or a stable token; never label a fabricated sequence as provider ID. Same approval number + partial cancellation can recur: if no stable event discriminator, mark ambiguous.
- Statement without provider row ID: fingerprint with versioned canonical fields and occurrence/multiplicity. Never claim provider-issued ID. If indistinguishable identical rows cannot be mapped uniquely to existing IDs, do not backfill them automatically. Compare multiset/count/amount separately; existing strong-ID endpoint cannot independently validate fingerprint rows and must not be reported as PASS for them.
- Scope fields: source_system, account_key, billing_month, amount_basis, source_record_id, source_record_id_type. Billing month comes from explicit statement/payment date, not approval date. For unbilled rows without a billing month leave unknown; do not infer or invent. Never double count purchase approval and its billed representation. Preserve actual stored amount meaning; if uncertain, leave unresolved.
- single-payment rows vs installment lines vs latest rows: collector to provide exact coverage and semantics, not assume all are distinct. Gross billed total, point deduction, net due and approval totals are separate.

## 3. Safe execution gate (to implement after agreement)
Do not use full /api/ingest upserts for legacy backfill; they can overwrite existing metadata and business fields. Implement dedicated authenticated metadata-only preview and apply with SQL transaction/RPC, allowlisted patch keys, immutable snapshot guards (id/external_id and expected updated_at or digest), server-side merge preserving user metadata, duplicate/conflict validation across target rows, audit before/after, dry-run digest tied to user-approved plan. Apply only exact_unique entries; abort whole batch on stale row, changed plan, duplicate or mismatch. No caller-supplied verification status or independent_verified flag. A fresh evidence collection time is not the historical source as_of. Separate backfill audit from ordinary source sync; do not fabricate a successful source run.
Before apply: user approval for plan, backup/snapshot and rollback design; test in isolated environment. After apply: verify same active IDs/count/business fields/memos, totals by scope, no duplicates, rerun read-only reconciliation, report unresolved records. Do not declare full reconciliation if any unmapped rows remain. Independent source proof remains separate.

## Current implementation
The read-only reconciliation now counts legacy rows lacking source_system as unresolved (unknown_source_records), rather than silently excluding them from the unmapped count. It does not assign their scope or modify data. Backfill endpoint and mutation are deliberately not implemented or executed yet; contract/preview plan must be agreed first.
