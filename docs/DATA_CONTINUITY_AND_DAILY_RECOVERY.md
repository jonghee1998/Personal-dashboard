# Published data continuity and daily recovery
- Ingest validation failures must never publish an empty/default/partial replacement. Last successful published rows remain authoritative until a complete verified scope is atomically published. A genuine verified zero is distinct from unknown or failed collection. Do not archive missing rows automatically.
- UI reads must validate complete API response, preserve in-memory last successful response on errors, and show unknown when no successful read exists rather than derived zero. No personal financial data cached in browser persistent storage. A hard reload during database outage cannot display a saved browser snapshot; durable server-side backup/read fallback is a later task.
- Monitor daily Samsung transaction, Samsung points, Naver points and news source separately. Latest failed/partial/quarantined report is shown as failure; source freshness is Seoul calendar day. A collector report is not independent proof or full-scope coverage. Original source timestamp stays unchanged on failure; DB timestamp is separate. No artificial advancement of as_of.
- Successful source refresh must be published even when the actual amount is unchanged; record genuine source confirmation time. Report each real attempt with run_id, source, scope, status, counts and error code. Failed collection must not be silently converted to success or 0.
- Collector daily recovery contract: per source expected schedule, retry transient failures (e.g. 15/60/180 minutes within source permissions and rate limits), preserve latest known valid snapshot, alert after repeated failure, record actual attempt outcomes. Do not fabricate a source report or evidence. Retry schedule must actually be configured in collector; this document is not proof that scheduling is active.
- Scope-specific source freshness and completeness are not equivalent. Existing legacy rows can have no provenance. Chart ends at latest observed registered day or source day, marks later days unknown rather than zero; no-row monthly total is unknown until complete coverage evidence supports a true zero. Existing totals remain registered-data totals, not bank statement totals.
- Next: server-side immutable staging, independent or user-approved evidence, atomic publish and metadata-only backfill with rollback, monitoring of overdue sources, isolated failure/recovery tests. Keep currently running collector compatible until a tested cutover.
